# 150. FW-трассировка iTrace/mstfwtrace: рабочий рецепт

Статус: рабочий рецепт (live, root-mellanox, CX-5 Ex 15b3:1019,
81:00.0/.1; циклы itrace 2026-10-08/09 и cx4lx-an 2026-10-09). Семантика
масок/классов/ограничения — `docs/250-re/100-formats/065-fw-trace.md`;
журналы-источники — `docs/superpowers/journal/2026-10-08-mstfwtrace-probe.md`,
`2026-10-09-irisc-itrace-v5r-nodata.md`,
`2026-10-09-irisc-itrace-l0-trace-task-03.md`,
`2026-10-09-cx4lx-an-fsm-task-01.md`.

## 1. Пререквизит: определить owner-функцию

Owner-функция трассера **недетерминирована per boot** — перед каждой
трассой определять заново (rebind-тест или BDF в raw ftrace-буфере;
dmesg `FWTracer` после rebind):

```sh
OWNER=0000:81:00.x     # текущий owner, не обязательно 81:00.0
```

Хвост по не-owner BDF = 0 событий без какой-либо ошибки. Ядренного
драйвера mlx5 (mainline) достаточно; OFED не нужен.

## 2. Рецепт (шаги + гейты)

```sh
# 1. ftrace-событие (включать вручную; до — enable=0):
echo 1 > /sys/kernel/debug/tracing/events/mlx5/mlx5_fw/enable
# 2. трасса (owner-функция!; маска+уровень строго парой):
timeout 120 mstfwtrace -d $OWNER -m ICMD -l 1 --ignore_old_events \
    > /tmp/fwtrace.log 2>&1 &
# 3. верификация маски маркером: mstreg GET MTRC_CAP на 81:00.0 каждые
#    ~5 c (ре-иссуя), до появления icmd_generic_reg_access (register_id=0x9040)
#    в /tmp/fwtrace.log. ВАЖНО: из состояния mask=0 маска применяется
#    с задержкой 16–18 с (наблюдено), возможно >30 с (механизм — открытый
#    след) — маркер-окно ≥ 18–20 c; между ненулевыми масками —
#    мгновенно. Каждый GET даёт ровно 1 icmd-событие + ~1 ts-update / 2 c.
# 4. restore (обязательно):
timeout 12 mstfwtrace -d $OWNER -m 0 -l 0
echo 0 > /sys/kernel/debug/tracing/events/mlx5/mlx5_fw/enable
```

Гейты:

- **Маркер до измерений**: без icmd-событий от маркеров маска не
  применена (startup race) — измерительное окно не начинать.
- **Верификация restore**: после mask 0 — mstreg ×2 + 15 c → 0
  mlx5_fw-событий в ftrace-буфере; буфер 0/0.

## 3. Чего избегать (флуд-ловушки)

- **all-classes (`-m 0xffffffff`)** — флуд 152K+ событий
  (`IRON populate_local_dbase`, ~каждые 80 µs; строка из db1/ROM) — ринг
  залипает.
- `-l 2` и выше — обходит class-маску, НО фильтрует L0/L1 (включая
  command-path): остаётся узкий кросс-классовый поток.
- **CMD_IF-биты с `-l 0` (например `-m 0x5000020 -l 0`)** —
  самоусиливающийся флуд: драйвер читает MTRC 0x9043 при EQ-обработке →
  каждый цикл даёт `access_reg 0x9043` (класс CMD_IF, site 0x000c756c) →
  291 988 / 400 781 событий за ~2-минутный maskscan (6 масок; `0x5000020
  -l 0` / `0xffffffff -l 0`). Работает только вместе с ICMD-битом
  (CMD_IF-only = 0 событий, ICMD-only = только command-path маркеры). При
  таком флуде **ftrace-кольцо перезаписывается за ~1 с** — нужные события
  дампить сразу, bounded-повторы.

## 4. Деградированный tracer-core: окно без живого дрена + ring-flush

Симптомы деградации (триггер — kill mstfwtrace в середине операции; одна
точка, воспроизводимость не проверялась): карточный ринг ПО-ПРЕЖНЕМУ
пишет события, но хост-дрен мёртв (EQ--reads
не идут); эмиссия сайта 0x9040 (MTRC_CAP-маркеры) и «TRACER: timestamp
update» умерли; nego/PDDR/module-FSM/isr_icmd-сайты живы. Маркеры для
такой карты = **PDDR GET (0x5031, `mstreg --reg_name PDDR --get`)** —
проходит при `-l 0`.

Рецепт окна (реализация — `scripts/probes/cx4lx-an/window3.sh`):

1. Гейт ДО окна обязателен (иначе окно молча пустое): PDDR-маркеры; на
   деградированной карте — gate-kick до проверки, **ABORT при 0 маркеров**.
2. Окно идёт штатно (без живого дрена события копятся в карточном ринге).
3. После WINDOW-END — mstlink-кики ПРИ живом mstfwtrace-хвосте
   (2× `mstlink -d <port> -m`, ~8 с между) выливают ринг в лог.
4. Restore (§2 шаг 4).

mstlink-контакт форсирует AN-рестарты партнёра (коллапс backoff ~96 c →
циклы 0.3–0.5 с; тот же класс форсажа, что module-FSM) — держать mstlink
строго ВНЕ измерительных окон.
