## 1. Отличия записи ITOC (`image_layout_itoc_entry`)

Структура/unpack: `tools_layouts/image_layout_layouts.h:862`,
`image_layout_layouts.c`. Отличия от FS3-записи (`020-fs3-sections.md` §1):

| Байт | FS3 | FS4 |
|---|---|---|
| 0x12-0x13 | reserved | **version** (bits 144-159) |
| 0x18 | reserved | bit7 = **encrypted_section** (bit 192) |
| 0x14 | rel(0x14.7) + flash_addr | только flash_addr (без rel) |
| 0x19 | no_crc(7), dev(6) | **crc-флаг** bits 205-207 (0x1 = CRC секции не считается) |

Остальные поля (type, size DW, zipped, clcrc, param0, param1, flash_addr
DW, section_crc @ 0x1A, entry CRC @ 0x1E) — те же.

## 2. ITOC-заголовок FS4 (`image_layout_itoc_header`)

`image_layout_layouts.h:937`. Доменные поля сверх FS3 (`015-fs3.md` §2):

| Байт | Поле |
|---|---|
| 0x10 | `flash_layout_version` (0/1, bit 128) |
| 0x13 | `version` (bit 152 — как в FS3) |
| 0x17 | `num_of_entries` (bit 184) |
| 0x1E-0x1F | header CRC |

Использование и эмпирика полей (2026-09-19, журнал
`2026-09-19-toc-meta-probe`; корпус 112 TOC):

- **flash_layout_version — единственное «живое» доп. поле заголовка**
  (mstflint читает И пишет): `AlignDeviceSections` (`fs4_ops.cpp:2078`) —
  требует ITOC flv == 1, иначе «Please update MFT package»; после
  выравнивания dev-секций ставит DTOC flv = 1 + ре-CRC заголовка
  (`:2272`); `CheckIfAlignmentIsNeeded` (`:2328`) — DTOC.flv < ITOC.flv →
  выравнивание нужно. Эмпирика: **flv=1 — CX-5 (16MiB), flv=0 — CX-6 /
  CX-6Dx (32MiB)** (в обоих TOC); в каждом образе ITOC.flv == DTOC.flv.
- **version** — mstflint НЕ валидирует (`CheckTocSignature` — только 4
  слова + header CRC); во всех наших TOC = **1**.
- **num_of_entries** — mstflint НЕ использует (итерация до `type=0xFF`,
  `fs4_ops.cpp:674-701`); заполняется не всегда: **0** у CX-5/CX-6,
  **29** (= число записей ITOC) только у CX-6Dx rel-22_50 (ITOC; DTOC — 0)
  → ненадёжный источник, cross-check только.

## 3. DTOC

`DTOC_ASCII 0x44544f43` — `fs4_ops.h:241`. DTOC — вторая TOC в **конце
флеша**; в ней — секции данных устройства. Эмпирика:

- 16МБ-флеш (CX-5): DTOC @ **0xFFF000**;
- 32МБ-флеш (CX-6Dx): DTOC @ **0x1FFF000**.

**32MiB-layout (верифицировано 2026-09-18,
`docs/superpowers/specs/2026-09-18-mlxini-ab-fs4-32mib-design.md` §1):**

- Слоты **16MiB**: A @0x0, B @0x1000000. Размер слота задан в образе:
  IMAGE_INFO (0x10) байт **+0x10B** = log_step (2^log_step = старт B;
  mstflint `new_image_start_addr = 1 << log2_chunk_size`,
  `fs4_ops.cpp:2511`): 16MiB-образы — 0x17, 32MiB-образы (CX-6Dx
  22.50.1002) — 0x18.
- Dev-данные размазаны по хвостам **обоих** 16MiB-половин: первая —
  0xd0 @0xf80000 (0x40000) + 0xf6/0xf7/0xf4/0xf5 @0xfc0000..0x1000000
  (в vendor-образах erased); вторая — 0xe5..0xed @0x1f00000..0x1ff8000
  + 0xE0 @0x1ff8000 + 0xE3 @0x1ff8140 + DTOC @0x1fff000 (19 энтри).
- 16MiB-дамп 32MiB-флэша: DTOC в дампе отсутствует; «slot B @0x800000» —
  вторая половина слота A (mlxfwutil `ab` — truncation-warning по
  log_step=24).

Обработка: `fs4_ops.cpp` (`CheckDTocArray`, `isDTocSection`,
`smallestDTocAddr`).

## 4. Специфика FS4

- **MAIN_CODE с clcrc**: в флеше каждая строка = 64B данных + 4B CRC
  (удаление при чтении — `fs4_ops.cpp:565-579
  RemoveCRCsFromMainSection`).
- **Boot record**: последние 4 байта boot-записи = CRC/аутентификация
  (`fs4_ops.cpp:588-601`).
- **Подпись v2**: при верификации подписи CRC MAIN-секции и boot record
  исключаются из подписываемых данных (`fs4_ops.cpp:603-628`).
- **Signed-образ** (CX-6Dx `.signed.bin`) содержит дополнительные секции:
  0xA6 FS4_RSA_PUB_KEY (0x1100), 0xA7 FS4_RSA4096_SIGS (0x600, crcf=1);
  у секций подписи `section_crc = 0x0000` и crc-флаг = 1.

## 5. Позиция ITOC — НЕ фиксирована

Эмпирика (пробник):

| Образ | ITOC | DTOC | Записей |
|---|---|---|---|
| CX-5 MCX512A (stock) | 0x5000 | 0xFFF000 | 25 |
| CX-5 Dell signed (09FTMY) | **0x4000** | 0xFFF000 | 25 |
| CX-6Dx signed | 0x5000 | 0x1FFF000 | 29 |

Все entry-CRC и header-CRC — OK. Вывод: позиция ITOC зависит от укладки
(размер boot, boot2, выравнивание) — парсер обязан искать, а не
хардкодить.

## 6. DTOC cert-секции по чипам (из 90 §5.1)

Эмпирика (скан DTOC всех локальных образов, `scripts/probes/toc_probe.py`,
2026-09-06):

- **CX-5 (16MiB, DTOC @0xFFF000): cert-секций НЕТ** — только device-данные
  (`FW_NV_LOG, NV_DATA0/2, DEV_INFO×2, MFG_INFO, VPD_R0`). Следствие:
  техника «заменить корневые сертификаты во флеше и подписать своим
  ключом» (класс CX-6) для CX-5 **неприменима в принципе** — root-of-trust
  не патчабельная flash-секция (вердикты —
  `docs/250-re/110-signing/030-root-of-trust.md` §3).
- **CX-6/6Dx**: cert-секции в DTOC есть (§3: 0xd0/0xed/0xee/0xf2/0xf4-f7),
  но в vendor-образах пусты; интроспекция 7 образов CX-6Dx (все cert-секции
  erased, единственный populated — 0xed DIG_CERT_PTR-каркас; «cert-assisted»
  опровергнута) — `docs/250-re/110-signing/055-cx6dx-signing.md` §6.
- `LC_INI_*` (0xef/f0/f1) отсутствуют во всех локальных образах ([постулат]
  вероятно, секции более новых чипов — CX-7/8/9).
