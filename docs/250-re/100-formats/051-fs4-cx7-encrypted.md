## 1. Две формы образа CX-7 — не одно и то же

| | Дистрибутив `.signed.bin` (28.50.1002) | Live-флеш (FNP true-physical, FB 28.34.4000) |
|---|---|---|
| Размер-модель | 32 MB «флеш-модель» | 32 MB физика |
| FS4-маг @0x0 | есть, version word `01 01` (rev 1.1) | два мага: слот A @0x0 **занулен**, слот B @0x1000000 intact (`01 00 01 00` @0x10) |
| ITOC | **нет нигде** (по всему 32 MB) | plaintext ITOC @0x6000 в каждом слоте (30 записей, CRC OK) |
| FW-пейлоад | единый блоб 0x93e580 B от 0x0, энтропия 8.00 | пер-секционно зашифрован внутри слота (~0x57F770) |
| @0x1000000 | маркер BE-длины блоба (`00 93 e5 80`) | **старт слота B** (полный FS4-маг) |
| DTOC | @0x1fff000, 19 записей | @0x1fff000, 14 записей |
| Прочее | device-область 0x1f00000+ plaintext; 0x1000010..0x1f00000 = 0xff | слот A + NV-хвост [0x57F770..0x6e666f], device-область 0x1f00000+ |

Вывод: `.signed.bin` — **контейнер доставки** (упаковка для burnEncryptedImage),
не образ физики флеша. Live-флеш — **двухбанковая A/B** (инвалидированный A +
активный B, каждый ~0x57F770) + FF-зазоры + device-область.

## 2. Контейнер доставки (mstflint-семантика)

- `IsEncryptedImage` (fs4_ops.cpp:138): образ «зашифрован», если ITOC-магии
  нет ни в одной из 2 известных позиций — дистрибутивы CX-7 попадают ровно
  в этот случай.
- `ENCRYPTED_BURN_IMAGE_SIZE_LOCATION_IN_BYTES = 0x1000000` (fs4_ops.h:48):
  маркер @0x1000000 = BE-размер зашифрованного burn-образа;
  `FwExtractEncryptedImage` (fs4_ops.cpp:2336) читает его и извлекает блоб
  0..0x93e580; `burnEncryptedImage` (fs4_ops.cpp:2444) шьёт (MCC/direct).
- Burn-гейт: `device_encrypted != image_encrypted` → hard error «Burning
  %sencrypted image on %sencrypted device is not allowed» (subcommands.cpp
  :2192/:3767; FS5-мисматч исключён). Коммит `2e83526f` («[burn-tools] bugs
  fixes») — до него encrypted-на-unencrypted шёлся свободно; pinned уже
  содержит.
- `.pldm` из zip — PLDM rev 1-обёртка того же блоба (байт-в-байт, без 16 B
  мага); `dc` на зашифрованном: «Operation not supported on an encrypted
  image»; verify зашифрованного флеша запрещён (fsctrl_ops.cpp:523).

## 3. Слот live-образа: структура (FB 28.34.4000, оба слота)

HW-указатели @0x18 (16×8B, mlxfwutil hw_pointers):

```
boot_record=0x100  boot2=0x7000  toc=0x16000  tools=0x500
digest=0x498b00(FS4_RSA4096_SIGS)  image_info=0x491680  image_sig=0x496680(SIG_512)
pub_key=0x497a00  hashes_table=0x15000  gcm_iv_delta=0xc52923e2 (константа образа)
```

| Офсет | Что | Примечание |
|---|---|---|
| 0x100 | boot_record (0x3f4 B [0x100..0x4f4)) | образ-константа (идентична между burn'ами); непрозрачен, без магии/DER/CRC (§8) |
| 0x6000 | **plaintext ITOC** | 30 записей; служебный для хоста — **boot-семантика = toc_ptr (0x16000)** |
| 0x7000..0x13e08 | boot2 (0xCE08 ≈ 52 KB) | образ-константа; непрозрачен (не компрессия/не iRISC — §8) |
| 0x15000..0x15804 | hashes-table (0x804 = канон 28×SHA-512) | зашифрована с байта 0 (live и дистрибьютор), образ-константа → keystream build-класса (§8) |
| 0x16000..0x163e0 | **зашифрованная копия ITOC** (0x3E0 = размер plaintext-ITOC) | per-burn различается; nonce/tag на флеше нет |
| 0x18000+ | секции по ITOC | шифротела + plaintext-зона метаданных 0x491680..0x499100 |
| 0x4916a4 | IMAGE_INFO: PSID `FB_0000000040` | plaintext |

Секции (ITOC, enc-флаги у всех 0 — шифрование фактическое, пер-секционное):

- **Plaintext**: IMAGE_INFO (0x10), SIG_256 (0xa0, пусто 0xff), PUB_KEYS_2048
  (0xa1), SIG_512 (0xa3), PUB_KEYS_4096 (0xa4), FS4_RSA_PUB_KEY (0xa6),
  FS4_RSA4096_SIGS (0xa7), ITOC, заголовок/HW-указатели.
- **Зашифрованы** (энтропия 7.82–8.00): все коды (MAIN 0x3dfc70, ROM_CODE
  0xb4428, BOOT3/IRON_PREP/PCI/PCIE_LINK/POST_IRON/UPGRADE), PHY (0x0A/0x0B/
  **0x0C PCIE_PHY_UC_CODE** 0xE90 @0x48c680 — слотов 0), CCIR (0x0D/0x0E),
  конфиги (0x08/0x09/0x11/0x12), 0x30 DBG_FW_INI, 0xE9 FS4_DEV_INFO3.
- **Ложно-plaintext** (низкая энтропия, но зашифрованы — по A/B-диффу и
  sec_crc): RESET_INFO (0x20), DBG_FW_PARAMS (0x32), APU_KERNEL (0x14),
  FORBIDDEN_VER (0xa2). Энтропия — недостаточный классификатор.

Хвостовая NV-зона слота A — плотный plaintext-экстент [0x580000..0x6e6670)
(перед ним FF; у слота B хвоста нет — FF): строковый пул main-FW
(`find_valid_nv_partition`, lifecycle/nvram, VNET), пути RISC-V-тулчейна,
код-подобное (не iRISC), VPD-дескриптор чужого варианта платы (400GbE).
Вне ITOC и DTOC, к секциям 0x08/0x09 отношения не имеет; природа — leftover
FW-контента, переживающий burn (запись/erase сверх образа нет). К
крипто-модели отношения не имеет (§8).

## 4. Per-burn шифрование (доказательство A/B)

Слоты A и B — два burn одного plaintext:

- идентичны: ITOC (все sec_crc), boot_record, boot2, hashes-table,
  plaintext-секции;
- различаются: шифротела секций, encrypted-TOC [0x16000,0x163e0), маг
  (A занулён = инвалидация слота, единственная).

→ шифрование рандомизировано per-burn — но только для класса enc-TOC +
шифротела секций: keystream'ы A/B глобально различны (989/992), а
nonce/tag на флеше отсутствуют (payload enc-TOC = вся запись 0x3E0,
вокруг FF). Зашифрованная hashes-table при этом A==B → её keystream
build-детерминирован (два класса — §8.1). `gcm_iv_delta` одинакова в
обоих слотах → различие не от delta; boot_record тоже A==B → per-burn
ключ/nonce — карт-локальный материал (§8.4). `sec_crc` в ITOC = CRC по
**plaintext** (stored-CRC шифротел не сходится; IMAGE_INFO OK).

## 5. CoRIM `.signed.cbor` (в zip дистрибутива)

- COSE_Sign1 (RFC 9052), ES384/SHA-384; payload = corim-map draft-12
  (tags 500/502/506): id `ConnectX-7_28.50.1002`, tag-id per-SKU, 7
  измерений: mkey 2–5 = sha-512-дайджесты (IANA ni-hash alg 8), mkey 6/7/8
  = raw-значения (версия/SKU-id).
- Подпись **verified** всеми 6 SKU публичным ключом
  `nvidia-corim-signer-cx7-id-2.pem` (docs.ndis.nvidia.com; sha256 PEM =
  thumbprint в самом манифесте; id-1 истёк 2025-03). Сертификатов внутри
  нет — только locator URL+thumbprint. Публичный ключ — только verify
  (ECDSA), к расшифровке отношения не имеет.
- **Дайджесты — по plaintext-компонентам сборки, не по шифротексту**:
  561 комбинация диапазонов дистрибутива (bin/pldm/zip/поддиапазоны) ×
  sha-512/sha3/shake — 0 матчей; класс-структура дайджестов зеркальна
  карте байтовых различий SKU (mkey2 ↔ блок 0x0-0x10000: 2 класса;
  mkey5 ↔ per-SKU-зоны: 6; mkey3/4 ↔ общий блоб: 1) → пер-компонентное
  детерминированное шифрование у дистрибутива (один plaintext → один
  шифротекст; contrast с per-burn у live). Манифест =
  reference-integrity-manifest для аттестации — **готовый оракул
  целостности для верификации будущей расшифровки**, не помощник самой
  расшифровки.
- mstflint про corim/cbor не знает ничего (0 упоминаний в дереве).

## 6. Read-политика live-карты (secure → FNP)

- **Secure-режим** (main FW): MCC/rb экспонируют только компонент-вью
  активного слота, логически с 0x0: окно ровно [0x0, 0x57F770) (= размер
  BOOT_IMG = конец последней секции ITOC); всё сверх — `out of flash
  limits` мгновенно. Внутри окна фильтрации нет (шифротекст отдаётся как
  есть). Параллель с MCDA-extent CX-5 (`110-signing/050` §2). Прямые пути
  закрыты: `--no_fw_ctrl` → `MFE_NO_FLASH_DETECTED`;
  `--flash_params`+`--no_fw_ctrl` → cr-space reject. `ri`/`dc` — только
  патченым тулингом с `--mcc_read` (4.37.0-1.3).
- **FNP** (strap): PCI-id `15b3:0218` [0580 Flash Recovery]; rb адресует
  всю 32 MB физику; q full — другой респондер (recovery/life-flash):
  раскрыл PRS Name (`cx7_CX71143DM_FB_4H_Eth_100g_1p_crypto_sb.prs`),
  MIC 2.0.0, Image/Device VSD, Boot Status; скрыл Rom Info/Encryption/
  SecureBootCapable (атрибуты main-FW — их отсутствие ≠ снятое шифрование).

## 7. Открытое / следствия

1. Рабочие секции (коды, конфиги, **0x0C**, 0x30) недоступны **в обеих
   формах** — нужен ключ, не парсинг. 0x0C-таблица CX-7 (Gen5) не извлечена.
2. Где живёт per-burn ключ/nonce — open; исключены boot_record и
   `gcm_iv_delta` (образ-константы, A==B) и запись enc-TOC (nonce/tag на
   флеше нет) → остаются fuse/OTP/device-область (§8.4). Загрузочная
   семантика ходит по toc_ptr=0x16000 (шифрованный ITOC), plaintext-ITOC
   @0x6000 — служебный для хоста.
3. CoRIM-дайджесты (4×sha-512 + версия + SKU-id, per-SKU классы) — эталон
   для проверки любой будущей расшифровки компонентов.
4. Дистрибутив: шифрование детерминированное per-component (5 SKU общий
   блоб); live: per-burn рандомизированное — один и тот же plaintext
   сборки даёт разные шифротексты на флеше.
5. Модель boot-криптографии, заполненная таблица дискриминации и вердикт
   об офлайн-расшифровке — §8 (цикл cx7-boot-crypto, 2026-11-10).

## 8. Аддендум (цикл cx7-boot-crypto, 2026-11-10): модель boot-криптографии

> Источник: журналы `2026-11-10-cx7-boot-crypto-task-01..05.md`; входы —
> дампы `refs/fw/cx-7/dumps/fb-28.34.4000/`, дистрибутив 28.50.1002,
> mstflint pinned a2b9858b. Провенанс улик: **[P]** первичная (прямое
> измерение на дампах/исходниках), **[S]** вторичная (вывод исключением
> на первичных фактах), **[H]** гипотеза. Энтропия как proof шифрования
> не используется (§3, ложно-plaintext).

### 8.1 Два класса keystream

Факты A/B (два burn одного plaintext в банках одной флеш) разделяют
шифрование слота на два класса (task-04 §1.4):

| Класс | Объекты | A vs B | Keystream |
|---|---|---|---|
| **per-burn** | encrypted-ITOC @0x16000, шифротела секций | ct A≠B (989/992 у TOC) | рандомизирован картой при burn [S] |
| **build-deterministic** | hashes-table @0x15000 (зашифрована с байта 0) | ct A==B байт-в-байт | детерминирован сборкой; общий между выходами пайплайна (кросс-SKU 28.50) [P] |
| неразличимо офлайн | boot_record, boot2 (opaque, A==B) | A==B | build-класс либо plaintext-opaque [H] |

Дистрибутив целиком — build-класс [P]: кросс-SKU-пара байт-идентична по
502/512 64K-блокам; диффы enc-TOC и hashes-table байт-локализованы ровно
в pt-полях (sec_crc/size/hash-слоты) — предсказание additive-stream при
общем keystream; ECB/XTS/CBC-с-переиспользованным-IV/tweak опровергнуты
частичными 16B-блоками. Режим: additive-stream семейство (CTR/GCM-класс)
— доказано для build-класса [P], перенос на live per-burn класс —
гипотеза высокой достоверности [S] (формат записи тот же).

| 6. Burn | хост шьёт/скачивает блоб as-is; карта перешифровывает per-burn класс на этапе FW verify/activate | as-is: fs4_ops.cpp:2336-2376 (raw extract), :2521-2611 (raw write); fsctrl_ops.cpp:918-921→933-961 (один компонент BOOT_IMG); fw_comps_mgr.cpp:1588 download → :1593 FW verify → :1634 FW activate [P]; «перешифровка на карте» — [S]: факты A≠B/A==B + кросс-SKU детерминизм (per-package рандомизации нет) |

Примечания модели: enc-флаги ITOC = 0 при фактическом пер-секционном
шифровании — флаги в образе политику не отражают [P] (§3); видимая
аутентификация per-burn записей на флеше отсутствует (SB-v2-окно enc-TOC
не покрывает, hashes-table — build-класс, per-line теги только у
cache_line_crc-секций) → проверка против карт-локального материала [S];
NV-хвост слота A — вне модели (leftover, §3).

### 8.3 Таблица дискриминации (спека §4.3), заполненная

| наблюдение (формулировка спеки) | фактический вердикт | (i) ключ в образе | (ii) KDF от образа | (iii) устройство/fuse |
|---|---|---|---|---|
| burnEncryptedImage шьёт блоб as-is, без перешифровки | хост — ДА as-is [P]; но слот ≠ файл: per-burn класс перешифрован картой [S] | − (per-burn ct не из файла) | ± | − в чтении «дистрибутив=слот» (механика на карте) |
| burn-flow перешифровывает на карте (FW/RNG) | **ДА**, селективно: per-burn класс; build-класс пишется как получен [S на P-фактах] | − | − | **+** |
| nonce одинаковые у A/B (один keystream) | опровергнуто: ksA≠ksB глобально (989/992) [P] | − (образ-константный nonce исключён) | − (KDF от образа дала бы один ks) | + (источник вне образа) |
| boot_record/boot2 несут wrapped-key/ключевое поле | не дискриминируется (opaque, A==B) [H] | ± | ± | ± — **open** |
| boot2 расшифровывается сам, содержит decrypt-рутину к fuse/CR | «сам» — нет (не plaintext-код) [P]; расшифровка внешним ключом [H] | − (как self-decrypt) | ± | + (внешний/карт-ключ) |
| plaintext-ITOC восстановим из enc-TOC знанием образа | **опровергнуто**: полный образ известен (все константы A==B), keystream не выводится [P] | **−** | **−** | **+** |

Итог: **(iii) устройство/fuse** — по совокупности: две независимые [P]-линии
против достаточности (i)/(ii) (ksA≠ksB при известном полном образе; nonce
вне флеша) + [S]-вывод перешифровки на карте. (i) как носитель wrapped
content-key **build-класса** (boot_record) не опровергнут [H] — но для
per-burn класса недостаточен в любом случае.

### 8.4 Вердикт об офлайн-расшифровке

- **Per-burn класс (enc-ITOC + шифротела секций live): офлайн-расшифровка
  по дампу невозможна без карт-локального ключевого материала.** Обе
  улики, потребованные семантикой вердикта, есть: (1) burn перешифровывает
  на карте [S — сильная совокупность: as-is исходники обоих путей хоста +
  факты A≠B/A==B + кросс-SKU детерминизм]; (2) источник per-burn вариации
  вне слот-образа [P — прямое измерение: все образ-константы A==B при
  ksA≠ksB; nonce/tag на флеше нет]. Остаточные гипотезы (вес честно):
  - «A/B из файлов разных билдов» (task-04 §3.3, «низкая уверенность») —
    сужено до **очень низкой**: кросс-SKU 28.50 показывает инвариантность
    ct обоих классов между выходами пайплайна, а hashes-table ct A==B
    (build-класс) ⇒ hashable-контент билдов идентичен; гипотезе нужен
    режим «рандомизация per-burn класса per-invocation при инвариантном
    build-классе» — единственное наблюдение пайплайна обратное.
    Проверяемый путь закрытия — дистрибутив 28.34.4000 (сверка ct
    build-класса слотов). Даже если гипотеза верна, ключ не в дампе:
    страдает только атрибуция (карта vs пайплайн NVIDIA), не вердикт.
  - карт-материал в device-области (DTOC: ea FW_INTERNAL_USAGE, eb/ec
    PROG_HW_FW), а не в fuse — одним дампом не дискриминируется;
    карт-локальность не меняет; кандидаты разбора для следующего цикла.
- **Build-класс (hashes-table live; дистрибутивный блоб): открыто.**
  Детерминизм доказан [P], источник keystream не установлен; boot_record
  (opaque) — кандидат wrapped-key [H]. Позитивного доказательства
  невозможности нет; офлайн-пробы формата исчерпаны (task-01/02),
  дискриминация требует внешнего ключа/алгоритма (ROM-путь, side-channel,
  утечка build-ключа).

### 8.5 Оракулы и задел будущих циклов

- **ITOC-пара** (pt @0x6000 ↔ ctA/ctB @0x16000): единственный
  known-plaintext оракул per-burn класса — 992 B keystream выводятся
  напрямую (ksA, ksB); любая гипотеза ключа/nonce проверяется байт-точно
  и мгновенно. Структура сужает пространство: nonce/tag вне флеша ⇒
  keystream невосстановим из записи даже при известном ключе — нужен
  per-burn nonce (у карты есть, у офлайн-аналитика нет).
- **CoRIM-дайджесты** (§5): готовы; применимы к дистрибьютору 28.50.1002
  (4×sha-512 plaintext компонентов) — верификатор будущей расшифровки
  build-класса; к live 28.34 неприменимы (другая версия).
- **hashes-таблица**: второй оракул — 28 слотов SHA-512 plaintext секций
  live-версии; заперт тем же build-ключом (таблица зашифрована),
  активируется после её расшифровки, затем верифицирует расшифровку тел.
- Follow-ups: (1) offline-разбор device-области/DTOC-секций на
  существующем дампе — поиск per-burn материала (гипотеза выше); (2)
  канон 035 дополнить «CX-7: hashes-table шифруется целиком, mstflint
  sizing по константам» (решение за владельцем); (3) live-цикл с
  контролируемым reburn и вторым дампом — прямая проверка per-burn
  рандомизации и инвариантности build-класса (отдельное решение
  владельца; с учётом no-fw-backup).

## 9. Аддендум (2026-11-14): предрелизные открытые образы CX-7

> Объекты: файлы `refs/fw/cx-7/dumps/cx7_firmware_dumps/` (в refs с
> 2026-11-12) — `28.33.0751/` (orig_firmware.bin
> + full_query/hw_query/ini) и `28.33.0800.bin` (md5 `828b3ce6…`).
> Промышленные дистрибутивы зашифрованы (§1–§2); предрелиз — единственный
> открытый plaintext-источник CX-7-контента. Инициатива —
> `docs/010-roadmap/200-securefw-bypass.md` (арка A); замеры ниже —
> 2026-11-14 (`mlxfwutil info`, grep, hexdump).
> Пополнение — арка securefw-arc-a (2026-11-14, журналы
> `2026-11-14-securefw-arc-a-task-01..06.md`): корпус T3/профиль,
> дифф 0751↔0800, формат boot2, boot_record-пара, FB-контейнеры
> (пункты ниже; выводы — «28.33-класс предрелиза, n=2», перенос на
> 28.34+ — только через дифф).

- **Формат**: FS4 32 MB, ITOC @0x8000 (29 записей, CRC OK), DTOC
  @0x1fff000 (14 записей) — парсится штатно. Все секции plaintext: коды
  (0x03 MAIN cl=1, 0x02/0x04/0x05/0x06/0x07, **0x0f FS4_BOOT3_CODE**
  0x2590/0x6a20), PHY (0x0A 0xDE50, 0x0B, **0x0C=0xE90**), CCIR
  (0x0D/0x0E — маркеры `ztr_rttcc` 2/7 вхождений: ид 190-арки-B extends
  на CX-7), **0x14 APU_KERNEL 0x581A0** (новый код-домен; в fb-дампе
  проходил как «ложно-plaintext» — §3), конфиги 0x08/0x09/0x11/0x12,
  подписи 0xA0–0xA7, 0x30, 0xE9.
- **boot2 @0x1000 — plaintext**: DW0=`0x20400040`, DW1=0x1201 →
  size=(4+0x1201)·4=0x4814; контейнер того же формата, что CX-6Dx
  (журнал 2026-09-20: тот же DW0). Стадия-2 модели §8.2 («boot2
  opaque»/не-iRISC 47.0%) установлена на зашифрованных fb-дампах — на
  предрелизе материал открыт для формат-идентификации (roadmap 200 A3).
- **boot_record @0x100 (0751) = разреженная init-таблица** CX-5/6-стиля
  (переход Carmel v1→v2, журнал 2026-09-20), НЕ непрозрачный CX7-blob
  0x3f4 (fb 28.34, §8.2) — пара «v1-style vs CX7-opaque» как материал
  разбора формата (roadmap 200 A4).
- 0x0C = 0xE90 совпадает с зашифрованным дистрибутивом (§3: 0xE90
  @0x48c680) → прогрессия размеров 0x0C как Gen-маркера (док 130 §5.3:
  2560→7808→78432) на CX-7 не продолжается: Gen5-механика PCIe PHY
  переехала/похудела (кандидаты — APU_KERNEL/BOOT3; open).
- **Смягчение выводов §7.1/§8.4**: «офлайн-анализ CX-7 невозможен» верно
  для зашифрованных дистрибутивов и per-burn live-слотов; предрелизные
  открытые образы дают полный plaintext (кроме fuse/ROM-домена).
- VPD_R0 (DTOC): size=0 @0x1ff8140, область стёрта (0xFF); VPD-строк
  (`PCIeGen`/`CSKU=`/`MLX:MN`) в MAIN_CODE нет — в отличие от
  CX-5/6/6Dx/6Lx (59/15/36/3 файлов корпуса) → VPD-механика CX-7 вне
  флеша (roadmap 200, арка C).
- **Корпус/дифф (арка A)**: оба образа — T3-witness'ы корпуса 190-A
  (md5-пины `scripts/corpus/manifest.py`, провизорный профиль `cx7`,
  load_base MAIN_CODE **0x20800000** — dc↔rt-база поколения отличается
  от CX-6Dx 0x21000000, брать из профиля); все 8 iRISC-prior секций
  декодируются (MAIN ratio 0.875), census 33 неизвестных опкода,
  PROFILE_DRIFT только 03 (op0x2e, 20/19 слов — не блокирует). Дифф
  0751↔0800 (разные SKU одной линейки: crypto+SB vs DGX-IPN-QA):
  **12 identical / 17 different / 0 absent**; MAIN_CODE 90.19%
  сравнимых байт, общих функций 249 из 12384/12491 → пересборка
  целиком, не точечный патч; CCIR-пара почти идентична и позиционно
  выровнена (0x0D 0.79% — изменена 1 функция из 15, 0x0E 6.41%);
  константы сборки байт-идентичны (07 UPGRADE_CODE, 0B/0C, 20, 32,
  A1–A7, E9) при различном дайджесте A0 (10%); A7
  FS4_RSA4096_SIGS идентичен при различном контенте кода — подписи не
  пересчитаны под контент либо константный блок (интерпретация
  открыта). Домены новых секций — `040-fs4-domains.md` §1 (0x0f =
  iRISC; 0x14 = данные, RISC-V APU-ядро: «ложно-plaintext» §3
  подтверждён как отдельный ISA-класс, не шифрование).
- **boot2 (арка A): plaintext iRISC в Carmel-контейнере.** Регион =
  `[DW0 8B header][body DW1×4 B][trailer-DW][CRC16-DW]`, парсится и
  CRC16-валиден (алгоритм mstflint `Crc16`, poly 0x100b —
  CheckBoot2-совместимо; 0751 0x4814 / 0800 0x4ed4); iRISC known-form
  98.6/98.7% (ref CX-6Dx 98.9%, random ~47%); энтропия тела 5.99/6.04
  — plaintext-класс (живой 28.34 opaque: 7.996). Не компрессия
  (zlib-raw/zlib/gzip/bz2/xz/lzma + lz4 block/frame/legacy, офсеты
  0..64 — 0 хитов; xxh32-чексуммы lz4 не верифицируются — граница
  метода), не RISC-V/ARM (паттерн-гистограммы на уровне random /
  известного iRISC). Кросс-дифф с CX-6Dx 22.50 (plaintext 0x3f2c =
  (4+DW1)·4): общий только контейнер-семейство DW0 (word-match 0.2%);
  0751↔0800 — общий пролог (6/8 головных слов, word-match 29.5%) при
  64.64% байтового диффа. Открытые наблюдения (не исследованы,
  bounded): trailer-DW 0x20400244 против 0x20400044 у CX-6Dx (бит
  0x200 — семейственное поле), стамп-нооп word0 тела (`addi
  zero,zero,<imm>` — кандидат build-id), слово 19. Вывод о
  28.33-классе (n=2): перенос «boot2 plaintext» на 28.34+ НЕ следует
  (28.34 — opaque с байта 0, §8.2).
- **boot_record (арка A): v1-style init-таблица в контейнере
  CX7-размера.** Экстент пары = ровно **0x3f4** =
  `getBootRecordSize(CX7)` (fs4_ops.cpp:4406) — тот же контейнер, что
  prod-opaque (fb 28.34, §8.2), заполнен разреженно: word0 0x418
  (семантика открыта), четыре CR-init записи (addr-класс 0x30d0xxxx —
  миграция с CX-6 0x1868xxxx, как у CX-6Dx; value-класс 0c1xxxxx),
  конфиг-блобы (в т.ч. 16B-блоб ровно дважды — CX-7-специфичная
  константа, в CX-5/6 refs отсутствует; ключ-материальная роль —
  [H]), zero-padding, трейлер tag16 @+0x3f0. Дифф пары 11 B / 7 слов
  = две первые CR-init записи (SKU-строфа) + счётчик @+0x214 +
  трейлер. **SB-V2-layout уже присутствует**: hashes_table_ptr=0x7000
  валиден (критерий V2, fs4_ops.cpp:5170), hashes-table @0x7000 —
  plaintext-карта `(section_id<<16 | slot_off)`, слоты с шагом 0x40
  (SHA-512-размер), skip-набор {A0,A1,A3,A4,A7} = mstflint; при этом
  SHA-512(raw flash bytes) == слот — 0 совпадений (все 24
  hashable-секции обеих сторон, обе базы декода) → база
  хэширования/шифрование слотов открыто; CRC16-семейство трейлера
  (6 алгоритмов × 3 спана × 4 образца) исключено офлайн — пробник
  `scripts/probes/securefw-arc-a/bootrec_trailer_probe.py` (+ тесты),
  трейлер остаётся tag16-классом с открытым алгоритмом/спаном.
  Гипотезы перехода v1-style → opaque [H1–H5] и список «что смотреть
  в 28.34+» — журнал `2026-11-14-securefw-arc-a-task-05.md` §5.
- **FB-контейнеры 28.35/28.36** (корень `refs/fw/cx-7/`,
  CX71143DMC-CDAE_FB 28.35.2250 / CX71343DAC-WEBF_FB 28.36.1010):
  @0x1000 = FF (boot2-регион стёрт/отсутствует); байтовая подпись
  ITOC-заголовка присутствует на **0x6000** (31/38 записей в таблице;
  ср. предрелиз — ITOC @0x8000, live-слоты fb-28.34 — plaintext-ITOC
  @0x6000, §3), но корпусной парсер (`mlxfwutil.Image()`) оба
  отвергает — «DTOC not found». Классификация «зашифрованный
  FB-контейнер, вне корпуса» (2026-11-14, журнал
  `2026-11-14-securefw-arc-a-task-01.md` §4): магия есть, но на
  нестандартной позиции, парсингу не подлежит.
